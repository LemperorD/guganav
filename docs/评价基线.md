# 评价基线

本文记录哨兵导航各模块的评价标准与基线采集方法。基线的作用是让「这次改动有没有变差」变成可核对的数字。文中尚未定稿的条目标为「待定」，采到数据后再补。

## 1 总则

### 1.1 判定指标

#### 1.1.1 总体结构

基线回答的问句是：在比赛条件下，导航链路能否让哨兵存活并到达指定目标；当不能时，是哪一个模块先失效。判定分为三块：

- 鲁棒性：长时间运行不垮，垮了能恢复。
- 地图测试：给定目标点，能不能到、多久到、撞不撞。
- 压力测试：在视觉满载和极端姿态下，定位精度和响应延迟是否仍在可接受范围。

模块级指标只用于归因，不单独作为比赛成绩。

#### 1.1.2 鲁棒性

单次运行上限按 30 分钟计，鲁棒性按 30 分钟一段试验。

- 长时间：30 分钟内不出现无法导航。
- 故障恢复：出现无法导航后 15 秒内恢复。恢复率目标 99%，最低 98%。
- 碰撞恢复：只统计恢复率，不统计发生率。碰撞分为撞静态障碍物和被其他机器人撞两类，两类分开统计。按运行时长分档测，看恢复能力是否随时间退化。
- 模块层：30 分钟一段，单模块不出现无法导航的目标 95%。
- 系统层：由模块层与恢复层推算，目标 99%。

碰撞检测用位姿突变加 IMU 加速度冲击，两个位姿的差突然拉大判为被外力推动。遥控接管期间下位机忽略导航指令，此时不判碰撞，切回自主后再开始。

#### 1.1.3 地图测试

三类场景逐层加变量：

| 场景类型 | 场景构成 | 通过率 | 碰撞次数 |
| --- | --- | --- | --- |
| 静态地图 | 先验地图，零额外障碍 | 100% | 0 |
| 复杂静态障碍 | 先验地图加先验地图里没有的静态障碍 | 100% | 最多 2 次 |
| 动态障碍 | 先验地图加脚本轨迹移动的障碍 | 100% | 最多 2 次 |

障碍物不能写进先验地图或 PCD，否则重定位和全局规划提前看到，测的就不是感知。

通过的定义：到达，且到达时间不超过基线时间加 10 秒，且碰撞次数不超过该类上限，且未被判为主动放弃。四个条件缺一个算失败。

- 到达：停位误差在容差内。容差暂定 10 cm 和 10°，待 benchmark 后调整。
- 到达时间：每张地图每类场景跑 10 次，去掉最高 2 次和最低 2 次，剩 6 次取平均作为基线时间。仿真与实车分开采集，按地图分别报，不合并。
- 主动放弃：单独记录触发原因，包括路径被堵、检测到碰撞、重规划次数用尽。为了不碰撞而停住不走，算主动放弃。

三类场景的地图新做，不使用现有地图。动态障碍按位置触发，不按时间触发，保证相遇点可重复。

#### 1.1.4 压力测试

压力条件来自真实输入的最坏组合，不人为拉高点云密度。

1. 视觉与导航同上位机，视觉跑最复杂模型，视觉输入固定成回放。回放数据待从视觉组获取。
2. 最大地图加最密静态障碍布置。
3. 动态障碍与目标频繁切换同时存在。
4. 极端姿态：允许范围内最剧烈的运动，具体动作待定。

指标：

- 定位精度：位姿输出与真实位姿的差，分位置误差和朝向误差。仿真用真值比对，实车用同一路线往返的重复性衡量。
- 响应：两条都记。串口到串口，起点是串口收到下位机数据，终点是串口发出速度指令。点云到串口，起点是点云消息的时间戳，终点是串口发出速度指令。在各地形处理、地图层、规划、平滑、控制的输入输出打时间戳，分段归因。

压力测试的结论只在「视觉满载」条件下成立，不与常规基线混报。

#### 1.1.5 启动成功率

每次启动统计一次，目标 100%，零缺陷。启动成功要同时满足三个条件：所有必备节点起来且没有反复重启；定位进入可用状态，里程计标定完成、重定位进入 `FINE`；导航能接收目标点并开始响应。三个条件缺一个算失败。

从进程启动到三个条件满足超过 60 秒算启动失败，60 秒为暂定值，采完基线后按实际启动耗时调整。冷启动和热启动分开统计，不合并。

### 1.2 记录方式

采集数据分两本账。

- 数据账：每帧一行，记位姿、速度、点数、时间戳。用来算到达时间、定位误差。
- 事件账：每发生一件事记一行，记损坏开始、恢复、碰撞、到达、主动放弃、规划失败。用来判通过和恢复。

时间字段记两个：消息里的 header 时间戳，以及节点实际收到或发出的时刻。只有前者不算不出处理延迟。

正文不存。点云存点数、包围盒、质心。代价地图存占用格数、未知格数、最大代价值。

存储格式为 JSONL，一段试验一个文件，首字段 `type` 区分 `event` 与 `frame`。

### 1.3 阈值怎么定

- 阈值由 benchmark 实测分布决定，不先拍。
- 基线时间取 10 次去头去尾平均，原始 10 个值一起留档。
- 新版本与基线比较时使用同一批地图、同样次数。两个版本的均值差要大于约两倍标准误，才算真实变化。
- 仿真与实车分别建立基线，不互相替代。
- 100% 是零缺陷要求，不是统计比例。任何一次失败都记为缺陷并归因，不能当作统计波动。

## 2 里程计

### 2.1 判定问题

里程计有两个目的，评价分两条线。

1. 计算位姿：位姿准不准、漂移快不快、跟不跟得上。
2. 生成点云：覆盖全不全、密度够不够、噪声大不大、有没有重影。

位姿线：与真实位姿的差，单位距离或单位转角累积的漂移量，单帧处理耗时是否满足 10 Hz 输入。

点云线：场景覆盖、每平方米点数、同一静止墙面的点云厚度、静止物体在不同帧里的错位。

### 2.2 输入与输出

输入为 IMU 与雷达点云。输出为位姿 `lidar_odometry` 与配准点云 `registered_scan`，下游为地形处理。

点云保存默认关闭，`pcd_save.pcd_save_en` 为 `false`。开启后由 `PriorMapManager` 写盘，默认路径为 `src/guga_localization/LIO/point_lio/PCD/scans_<时间戳>.pcd`；配置了 `pcd_save.path` 时以它为基准路径。该机制与 GICP 定位状态联动：状态为 SUSPECT 时累积新扫描，状态为 LOST 时写盘并调用重载服务，用于在线建图与丢失后恢复。所以点云不只是建图模式的产物，导航过程中也可能增量写入。

### 2.3 采集字段

数据账每帧记：

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| stamp | 点云消息时间戳 | 对齐真值、算延迟 |
| recv_time | 节点收到点云的时刻 | 算处理耗时 |
| pos_x, pos_y, pos_z | 位姿位置 | 位置误差 |
| quat_x, quat_y, quat_z, quat_w | 位姿四元数 | 朝向误差 |
| lin_vel_x, lin_vel_y, lin_vel_z | 速度 | 速度质量 |
| ang_vel_x, ang_vel_y, ang_vel_z | 角速度 | 速度质量 |
| cloud_points | 配准点云点数 | 规模与吞吐量 |
| latency_ms | 节点内计时 | 实时性 |

事件账记：标定完成、点云丢帧（相邻点云间隔超过 0.2 秒）、IMU 断流（超过 0.1 秒没有 IMU）、PCD 写盘（SUSPECT 累积、LOST 写盘）。

### 2.4 判定指标

| 指标 | 用什么数据 | 怎么算 |
| --- | --- | --- |
| 吞吐量 | 配准点数、单帧处理耗时 | 点数除以耗时，单位点每秒 |
| 端到端时间 | 点云时间戳、位姿发出时刻 | 两者之差 |
| 抖动 | 每次的端到端时间 | 端到端时间的标准差 |
| 漂移 | 位姿、真值、累计路程与转角 | 累计位置误差除以路程，累计朝向误差除以转角 |
| 绝对精度 | 位姿与真值的逐帧差 | 位置与朝向误差的均方根、95 分位、最大值 |
| 时间戳一致性 | 位姿 header 时间戳、融合用的点云时刻 | 两者之差 |
| 输出频率 | 发布帧数、总时长 | 帧数除以时长 |
| 覆盖 | 场景已知几何、点云 | 场景表面被点云覆盖的面积比例 |
| 密度 | 点数、覆盖面积 | 点数除以覆盖面积 |
| 噪声 | 同一平面上的点 | 点到拟合平面的距离标准差 |
| 重影 | 同一静止物体在两帧中的位置 | 两帧中心点的位移 |

仿真里绝对精度和漂移用合成真值算。实车里没有真值，只能用闭合回路：走一圈回到出发点，用回到原点的误差除以路程作为漂移估计，绝对精度无法直接测，只报闭合误差。

## 3 重定位

### 3.1 判定问题

重定位在里程计漂移后，用先验点云地图把位姿拉回全局系。它输出的是 `map -> odom` 修正量，不是持续位姿，所以评价重点是修正对不对、恢复快不快。

1. 修正准不准：看配准残差 RMSE 和收敛后位姿与真值的距离差。
2. 恢复快不快：从 `SUSPECT` 或 `LOST` 回到 `FINE` 的时间。
3. 拉不拉得回来：人为制造漂移后能否收敛回正确位置。

### 3.2 输入与输出

输入是 `registered_scan` 和 `initialpose`。输出是 TF `map -> odom`（20 Hz）、`gicp_state`（`0=INITIAL`、`1=FINE`、`2=SUSPECT`、`3=LOST`）、`gicp_lost`（1 Hz）。

状态机为 `INITIAL -> FINE`；`FINE` 下残差超过 `error_max` 进入 `SUSPECT`；`SUSPECT` 持续超过 `suspect_state_timeout_sec` 进入 `LOST`；之后 GICP 合格可回到 `FINE`。

### 3.3 采集字段

事件账：状态迁移（时刻、从哪个状态到哪个状态）、每次 GICP 的残差 RMSE、每次 GICP 的耗时、本次修正量（平移与旋转）。

数据账：`map -> odom` 的平移与四元数、对应时刻。

### 3.4 判定指标

| 指标 | 用什么数据 | 怎么算 |
| --- | --- | --- |
| 修正精度（配准 RMSE） | 每次配准的残差 | 均方根 |
| 修正精度（距离差） | 收敛后位姿、真值 | 欧氏距离 |
| 收敛时间 | 状态迁移时刻 | 进入 `SUSPECT` 或 `LOST` 到回到 `FINE` 之差 |
| 重定位成功率 | 漂移档位、收敛后位姿、真值 | 距离差在容差内的比例 |
| GICP 单次耗时 | 节点内计时 | 中位数、95 分位 |

成功率测试矩阵：

| 漂移类型 | 档位 |
| --- | --- |
| 平移 | 0.5 m、1 m、2 m |
| yaw | 15 度、30 度、45 度 |

成功标准是收敛回 `FINE` 后，位姿与真值的差在容差内。容差暂定 10 cm 和 5 度，采完基线后调整。

实车没有真值，用场地里量好的标杆位置作参照；没有标杆时只报往返闭合误差。

### 3.5 已知缺口

- 不测 yaw 大于 90 度的漂移。这类偏差下 GICP 依赖初始位姿，容易收敛到错误方向，另行处理。
- 不单独统计误匹配率。锁错位置靠距离差筛掉，收敛到错误位置时距离差会变大。

## 4 地形与地图层

### 4.1 判定问题

地形处理把点云转成高度与障碍点，地图层把障碍点写进代价地图并做标记、清除、膨胀。两层的输出形态不同，但串在同一条链路上，所以合并成一章，评价从点云输入到代价地图输出的这条链路。

障碍输出在两层各有一道阈值。`terrain_analysis` 内部按 `minObstacleHeight` 粗筛，默认 0.04 m，只有超过这个高度的点写进 `terrain_map`。`obstacle_layer` 再按 `min_obstacle_height` 和 `max_obstacle_height` 过滤，默认 0.0 到 2.0 m。所以「漏判、误报」的最终结果跨两层，归因时要分清是高度算错，还是某一层的阈值设错。

### 4.2 输入与输出

输入是 `lidar_odometry` 和 `registered_scan`。输出是 `terrain_map`，其中 `intensity` 为点距局部地面的高度；还有 `terrain_returns_current`，只用于代价地图射线清除，`intensity` 恒为 0。

### 4.3 采集字段

数据账每帧记：帧时间戳、输出点数、输出点的高度统计（均值、最大值）、处理耗时。

事件账记：输出为空、点数骤降到零、清除射线为空。

### 4.4 判定指标

| 指标 | 真值来源 | 怎么算 |
| --- | --- | --- |
| 障碍标记正确率 | 合成场景的障碍几何 | 真实障碍最终被标进代价地图的比例 |
| 误报率 | 合成场景的可通行区域 | 可通行区域被标成障碍的比例 |
| 清除正确率 | 移走障碍后的场景 | 障碍移走后格子被清掉的比例 |
| 残留率 | 移走障碍后的场景 | 障碍移走后仍留在代价地图里的格子比例 |
| 高度误差 | 合成场景的真实离地高度 | `intensity` 与真实高度的差，取均方根和最大值 |
| 可通行宽度 | 障碍物与膨胀半径 | 膨胀之后窄通道剩下的可通过宽度 |
| 端到端延迟 | 两个时间戳 | 点云输入到写进代价地图的时间 |
| 覆盖 | 场景中有输入的区域 | 有点云输入的区域中被最终标出的比例 |
| 时间一致性 | 重复处理同一场景 | 多次输出之间代价地图的差异 |

地形处理和地图层的耗时分开记，一帧的端到端延迟里，地形输出时刻和地图层写入时刻各打一个戳。端到端延迟变长时，能看出是哪一段慢。

时间一致性受 `decayTime` 这类衰减参数影响，测的时候参数要固定，报告里写明取值。

### 4.5 已知限制

实车没有合成场景的真值，标记正确率和误报率只能用人工摆放的已知障碍测：量好位置和尺寸的箱子放在已知坐标上，看代价地图有没有标出这些位置，有没有把旁边空区域误标。清除正确率可以用移走箱子后的场景测。这样测出来只覆盖摆放的障碍，不覆盖场景里其余障碍。高度误差实车也测不了，只做一致性。

## 5 规划器

### 5.1 判定问题

规划器是 Nav2 的全局规划插件，默认实现是 `jps_planner`。它由 `planner_server` 调用 `createPlan(start, goal)`，输入起终点和代价地图，输出 `nav_msgs::Path`。评价分两类：成功率回答「做没做成」，计算指标回答「做得多好」。

### 5.2 输入与输出

输入是起终点、代价地图，以及可选的 ESDF 距离场。输出是 `nav_msgs::Path`。

内部流程是 JPS 搜索、贴障碍对角修正、短路径补密、B-spline 平滑、碰撞校验。平滑路径碰撞时退回线性 JPS 路径，最终仍碰撞时返回空路径。

### 5.3 采集字段

事件账每次规划请求记一行：起终点、耗时、是否返回非空路径、是否触发平滑回退、最终路径是否碰撞。

数据账记输出路径的点数和路径长度。

### 5.4 判定指标

| 指标 | 怎么算 |
| --- | --- |
| 规划成功率 | 有解起终点对中，返回非空路径的比例 |
| 规划耗时 | 中位数、95 分位 |
| 次优性 | 路径长度除以最短路径长度 |
| 碰撞率 | 返回路径与障碍相交的比例 |
| 平滑回退率 | B-spline 平滑后碰撞、退回线性路径的比例 |
| 最小间距 | 路径离障碍的最近距离 |
| 平滑度 | 路径最大曲率或最大转角 |

碰撞率和平滑回退率是否合并成一项，待定。

## 6 控制器

### 6.1 判定问题

控制器输入路径和位姿，输出 `cmd_vel`。它不能离线检查结果，必须让底盘实际跑起来，拿实际轨迹和期望路径比，所以是闭环评价。

`guga_controller` 下有三套控制器：MPPI、MPC、PID Pursuit。三套都测，以 MPPI 为基准。MPPI 的基线先采，另外两套用同一批场景、同样的路径测，结果和 MPPI 比。

### 6.2 输入与输出

输入是 `nav_msgs::Path` 和当前位姿。输出是速度指令 `cmd_vel`。

### 6.3 采集字段

数据账每帧记：实际位姿、实际速度、指令速度、时间戳。

事件账记：到达终点、偏离路径超过阈值、速度发散。

### 6.4 判定指标

| 指标 | 怎么算 |
| --- | --- |
| 跟踪精度 | 实际轨迹与路径的横向误差，实际朝向与路径切向的差 |
| 速度跟踪误差 | 实际速度与指令速度的差 |
| 平滑度 | 实际加速度、加加速度的大小 |
| 收敛时间 | 偏离路径后回到路径的时间 |
| 成功率 | 给定路径走完并到达终点的比例 |
| 计算耗时 | 一次求解的耗时，中位数和 95 分位 |

MPPI 和 MPC 的耗时随参数和场景变化，PID Pursuit 没有求解器，三套的耗时不在一个量级上，只能各自和自己的基线比。

## 7 平滑器

### 7.1 判定问题

平滑器把稀疏航点变成连续轨迹。`bspline_optimizer` 是纯 C++ 库，输出 7 阶 B-spline；`pb_minco_smoother` 是 Nav2 插件，输出 `MincoTrajectory` 多项式轨迹，给 MPC 控制器用。规划器内部的 B-spline 平滑调用的就是 `bspline_optimizer`，这一章评价「航点变连续轨迹」这一步。

### 7.2 输入与输出

输入是 JPS 给出的稀疏航点或路径。输出是平滑后的 B-spline 或 `MincoTrajectory`，带每段的持续时间和多项式系数。

### 7.3 采集字段

数据账记：输入航点数、输出轨迹段数、总时长、轨迹最大曲率、最大加加速度、计算耗时。

事件账记：输出轨迹碰撞、输出为空、约束超出上限。

### 7.4 判定指标

| 指标 | 怎么算 |
| --- | --- |
| 平滑度 | 轨迹曲率和加加速度的大小 |
| 约束满足 | 速度、加速度、曲率是否在设定上限内 |
| 碰撞 | 优化后的连续轨迹是否穿障碍 |
| 拟合偏差 | 平滑轨迹与原始航点的偏离量 |
| 计算耗时 | 一次 `fit` 加 `optimize` 的时间 |
| 成功率 | 给定航点输出有效轨迹的比例 |

## 8 通信

### 8.1 判定问题

通信这一章测 ROS 2 节点之间消息传递的开销，不测串口驱动。它回答「通信不是瓶颈」这句话能不能成立。

### 8.2 输入与输出

评价对象是关键话题的发布端与订阅端，包括点云、代价地图、路径、`cmd_vel`。这些话题的消息大小差几个数量级，分开测。

### 8.3 采集字段

每条消息在发布端打一个时间戳，在订阅端回调入口再打一个。数据账记这对时间戳、消息大小。

### 8.4 判定指标

| 指标 | 怎么算 |
| --- | --- |
| 发布到订阅延迟 | 订阅端回调时刻减发布端发出时刻 |
| 吞吐量 | 单位时间传递的消息条数，对照该话题的发布频率 |
| 序列化耗时 | 消息转成字节的时间 |
| 丢消息率 | 发布数量与订阅数量之差的比例 |
| CPU 占用 | 通信线程占用的 CPU |
| QoS 对齐 | 发布端与订阅端的可靠性、历史深度、持久性、截止时间是否兼容 |

QoS 对齐要查四项：可靠性（BEST_EFFORT 对 RELIABLE 不兼容）、历史深度、持久性（TRANSIENT_LOCAL 与 VOLATILE 混用会让晚加入的订阅者收不到历史消息）、截止时间和寿命。
