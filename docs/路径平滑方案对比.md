# B-spline 与 MINCO 路径平滑方案对比

本文对比项目中的两种路径平滑方案：`bspline_optimizer` 和
`pb_minco_smoother`，说明它们的定位、优缺点、当前接入状态及推荐用法。

## 1. 当前项目状态

### 1.1 B-spline

`bspline_optimizer` 是一个纯 C++ 几何路径优化库，由 `jps_planner` 直接调用。
当前仿真和实车 JPS 配置均设置了：

```yaml
GridBased:
  enable_bspline: true
```

因此选择 JPS 作为全局规划器时，当前处理链路为：

```text
JPS 搜索
  -> 路径补密
  -> B-spline 拟合
  -> 可选的 ESDF 梯度优化
  -> 碰撞检查
  -> nav_msgs/Path
```

相关实现：

- [`bspline_optimizer`](../src/guga_planner/bspline_optimizer/)
- [`jps_path.cpp`](../src/guga_planner/jps_planner/src/detail/jps_path.cpp)
- [`jps.yaml`](../src/guga_bringup/config/reality/planner/jps.yaml)

> 历史上的 `bspline_opt` 已改名为 `bspline_optimizer`。工作区里的
> `B-spline_opt` 只是改名后残留的空目录，不是另一套算法，也不参与编译。

### 1.2 MINCO

`pb_minco_smoother` 实现了标准 `nav2_core::Smoother` 接口，由 Nav2
`smoother_server` 加载。当前已作为可选链路接入，但不是默认方案：

```bash
# 默认：保留规划器内部平滑；JPS 使用 B-spline
scripts/simulation.sh nav rmuc_2025 planner:=jps smoother:=planner

# 可选：关闭 JPS B-spline，改用 MINCO
scripts/simulation.sh nav rmuc_2025 planner:=jps smoother:=minco
```

`smoother:=planner` 使用原行为树，不调用 Nav2 `SmoothPath`；
`smoother:=minco` 切换到带 `SmoothPath` 的行为树，并加载
`pb_minco/MincoSmoother`。实车脚本使用相同参数形式。

相关实现：

- [`pb_minco_smoother`](../src/guga_planner/pb_minco_smoother/)
- [`config/smoother/minco.yaml`](../src/guga_bringup/config/smoother/minco.yaml)
- [`navigate_to_pose_w_replanning_and_recovery.xml`](../src/guga_bringup/behavior_trees/navigate_to_pose_w_replanning_and_recovery.xml)
- [`navigate_to_pose_w_replanning_smoothing_and_recovery.xml`](../src/guga_bringup/behavior_trees/navigate_to_pose_w_replanning_smoothing_and_recovery.xml)
- [`navigate_through_poses_w_replanning_and_recovery.xml`](../src/guga_bringup/behavior_trees/navigate_through_poses_w_replanning_and_recovery.xml)

## 2. 核心区别

| 维度 | `bspline_optimizer` | `pb_minco_smoother` |
|---|---|---|
| 主要定位 | 几何路径平滑 | 带时间参数的轨迹优化 |
| 曲线表示 | 7 阶 B-spline | 分段多项式 MINCO |
| 接入位置 | JPS Planner 内部 | Nav2 `smoother_server` |
| 适用规划器 | 当前专门服务 JPS | 可以处理任意规划器输出 |
| 平滑目标 | 曲率、路径偏差 | jerk、时间、避障和动力学可行性 |
| 避障方式 | Costmap、ESDF、控制点投射 | 从 Master Costmap 生成局部 ESDF，并加入软代价 |
| 碰撞保证 | 输出后硬碰撞检查，失败时回退 | 主要依赖软代价，应启用 Nav2 输出碰撞检查 |
| 速度/加速度 | 不显式处理 | 作为软约束参与优化 |
| 时间优化 | 无 | 有 |
| 输出 | 采样后的 `nav_msgs/Path` | `nav_msgs/Path` 和 MINCO 多项式消息 |
| 当前成熟度 | 已接入、有测试和回退逻辑 | 已作为可选项接入并通过插件加载验证，尚缺轨迹效果和实车验证 |

## 3. B-spline 方案

### 3.1 优点

- 已经与 JPS 的稀疏跳点、路径补密和碰撞回退逻辑集成。
- 可以有效减弱 JPS 路径中的折线、锯齿和方向突变。
- 支持使用 ESDF 梯度将路径推离障碍物。
- 平滑后会执行硬碰撞检查；结果碰撞时可回退到线性 JPS 路径。
- 参数数量相对较少，调试和维护成本较低。
- 已有单元测试、联合测试、性能数据和可视化结果。
- 不依赖 `smoother_server` 或行为树修改，当前链路较简单。

### 3.2 缺点

- 只优化几何路径，不是真正的时间轨迹。
- 不显式约束机器人速度、加速度和 jerk。
- 在急转弯或障碍物附近可能出现切角、过冲，需要补密、投射和碰撞回退。
- 当前实现与 JPS 深度绑定，不能直接作为其他规划器的统一后处理器。
- 输出是按参数采样的 `Path`，没有每个路径点的到达时间。
- 当前梯度优化包含较多数值计算，控制点较多时仍需关注耗时。

## 4. MINCO 方案

### 4.1 优点

- 同时优化平滑度、避障、速度、加速度和运行时间。
- 轨迹具有明确的时间参数，更接近机器人实际执行的运动轨迹。
- 通过最小化 jerk，使速度和加速度变化更加连续。
- 采用标准 Nav2 Smoother 插件接口，可统一处理 JPS、Smac 等规划器输出。
- 支持根据里程计和上一条轨迹进行连续重规划，减少轨迹切换跳变。
- 可以发布完整的 MINCO 多项式系数，便于支持时间轨迹的控制器直接使用。

### 4.2 缺点

- 采用两阶段 L-BFGS 优化，计算负担和最坏耗时通常高于单纯几何平滑。
- 参数和权重较多，平滑、避障、动力学、时间目标之间需要联合调参。
- 速度、加速度和安全距离是软约束，不能单独作为绝对安全保证。
- ESDF 快照更新失败时可能退化为无避障优化，必须增加输出碰撞检查。
- 当前项目尚无针对该插件的轨迹回归测试、仿真基准和实车运行记录。
- 示例配置部分过时，例如 `waypoint_interval` 并未被当前代码读取。
- 默认里程计话题是 `/odom`，而本项目使用 `odometry`，接入时必须修改。
- 当前控制器只消费采样后的 `Path`，没有订阅 MINCO 多项式消息，因而无法完整利用时间轨迹优势。

## 5. 是否重复

两者在以下功能上明显重叠：

- 将离散或折线路径转换为连续曲线；
- 降低路径的方向和曲率突变；
- 利用 ESDF 或 Costmap 远离障碍物；
- 输出供控制器跟踪的平滑路径。

MINCO 额外提供时间分配、速度、加速度和 jerk 优化。因此它可以替代 B-spline
承担后端轨迹优化，但不建议在正常运行链路中依次执行两者：

```text
JPS -> B-spline -> MINCO -> Controller  # 不推荐
```

这种串联会重复进行几何平滑和避障优化，增加规划延迟，而且第二个优化器可能改变
第一个优化器已经验证过的结果。

## 6. 推荐方案

### 6.1 保持当前稳定方案

如果目标只是获得可跟踪的平滑 JPS 路径，继续使用：

```text
JPS -> B-spline -> Controller
```

该方案已经接入、测试并具备碰撞回退逻辑，当前风险最低。

### 6.2 验证 MINCO

如果目标是获得带速度、加速度和时间约束的轨迹，建议在独立仿真配置中使用：

```text
JPS（enable_bspline: false）
  -> Nav2 SmoothPath 动作
  -> MINCO
  -> Controller
```

上述切换已经由第四层 `config/smoother/*.yaml` 和启动参数完成：

- `smoother:=planner`：使用原行为树，并保留规划器内部平滑；
- `smoother:=minco`：关闭 JPS B-spline、加载 MINCO、选择带平滑步骤的行为树；
- MINCO 插件实例明确命名为 `MINCO`，行为树通过 `smoother_id="MINCO"` 只请求该插件；
- `odom_topic` 已设置为 `odometry`；
- 行为树设置 `max_smoothing_duration=0.8` 并启用输出碰撞检查；
- MINCO 行为树的重规划频率限制为 `0.5 Hz`，避免两阶段优化长时间占用 CPU；
- MINCO 两阶段迭代次数初始均限制为 30，后续依据基准测试调整；
- 第一阶段和整体优化分别使用硬截止时间，超时后会在代价函数计算中主动中断；
- Costmap ROI 未变化时复用 ESDF，不再重复执行两次精确距离变换；
- 默认关闭 MINCO 调试轨迹和 Marker 发布，需要调试时再将 `publish_trajectory` 打开；
- MINCO 超时、优化失败或输出碰撞时，行为树自动回退到未平滑的规划器路径，不会阻断整次导航。

针对 MINCO 模式旋转时的间歇性“鬼点”，`scan_to_sensor_frame`
也改为原子消费同一帧的点云、里程计位姿、坐标系和时间戳。TF 查询
失败时丢弃该帧，不再使用单位变换回退，以免旧点云在新位姿下被错误投影。

这种结构允许以后增加其他平滑器：新增一份 smoother YAML，并扩展脚本与 launch
的合法选项即可，无需复制 planner/controller 组合配置。

### 6.3 完整发挥 MINCO 能力

如果控制器仍只跟踪 `nav_msgs/Path`，MINCO 的时间分配结果会在路径采样后部分丢失。
若要完整利用 MINCO，应进一步让 MPC 或其他控制器消费其多项式轨迹和时间信息，
并根据轨迹的期望位置、速度和加速度进行跟踪。

## 7. A/B 验证指标

不要只比较 RViz 中的曲线是否好看，至少记录以下指标：

| 指标 | 目的 |
|---|---|
| 平滑耗时 P50/P95/最大值 | 判断能否满足当前重规划频率 |
| 规划成功率与超时率 | 判断优化器稳定性 |
| 路径长度 | 避免过度绕行 |
| 最小障碍物距离 | 验证安全裕量 |
| 最大曲率和曲率变化 | 衡量几何可跟踪性 |
| 最大速度、加速度和 jerk | 衡量动力学可执行性 |
| 横向跟踪误差 | 衡量控制器实际跟踪效果 |
| `cmd_vel` 抖动和饱和次数 | 衡量平滑是否真正改善控制输出 |
| CPU 占用与规划线程阻塞时间 | 判断实车算力是否足够 |
| 输出碰撞或回退次数 | 衡量避障优化可靠性 |

最终选型应以相同地图、相同起终点、相同控制器和相同速度限制下的重复测试结果为准。
