三点直接推论：

1. **比赛期间没有任何人工注入信息的通道。** 初始位姿、目标点、模式切换都必须由车载程序自行决定，RViz 的 2D Pose Estimate 只能作为赛前调试手段。
2. **不存在雷达与飞镖。** U26 全文出现"雷达"0 次、"飞镖"0 次，因此 RMUC 里经雷达信息波获取敌情的链路在 RMUL 不存在（见 §5）。
3. **多机通信被禁止。** 队友信息只能来自裁判服务器下发的 `0x020B`，不能自建机器人间链路；另受 R3（禁止自行架设无线设备）与 R14（进场人员不得与外界通信）约束。

## 4. 结构性空槽位：协议有字段、RMUL 无对应实体

P26 是跨赛事共用的协议，字段未必对应 U26 的机制。下表各项在本赛季**不要按存在来设计**，需先答疑确认：

| 协议位置 | 字段 | 情况 |
| --- | --- | --- |
| `0x0003` | 双方前哨站、基地血量 | U26 全文无"前哨站""基地" |
| `0x0101` | 堡垒、前哨站、基地、能量机关相关状态 | U26 无"堡垒""能量机关"；RMUC 的中心增益点等字段 U26 未描述 |
| `0x0105` | 飞镖发射与命中 | U26 无"飞镖" |
| `0x0208` | 堡垒储备 17mm 允许发弹量 | U26 无"堡垒" |
| `0x020B` | 工程机器人、4 号步兵坐标 | 3V3 阵容无工程与 4 号步兵 |
| `0x020D` | 当前姿态、立即复活资格与金币、远程兑换次数、能量机关可激活标记 | U26 中"姿态""立即复活""远程兑换""能量机关"均为 0 次出现（对照 R26 分别为 16、12、25 次） |
| `0x0120` 子内容 | 哨兵确认复活、兑换立即复活、远程补弹/回血、姿态切换 | U26 的复活是自动读条，未要求"确认复活"；其余动作在 U26 无机制 |
| `0x020C`、`0x020E`、`0x0305`、`0x0A01`–`0x0A06` | 雷达标记、雷达自主决策同步、雷达到选手端数据、雷达信息波 | U26 无"雷达"，这些帧与链路在本赛季无发送方 |
| `0x0301` 子内容 `0x0200`–`0x02FF` | 机器人之间通信，哨兵接收上限 5120 字节/1000 ms | 协议提供，但 U26 表 3-4 对哨兵写明"多机通信：不允许"，本赛季不可用 |

## 5. 队友与敌方信息的来源边界

队友：只有 `0x020B` 一条官方来源，1 Hz、二维坐标、无速度、无意图、无血量（血量在 `0x0003`）。RMUL 下不能自建机器人间链路，因此"队友在做什么"只能靠位置序列推断，且 1 Hz 的坐标序列对快速机动的队友几乎无法估计速度。

敌方：**没有任何官方来源。** RMUC 走的是雷达信息波（`0x0A01`–`0x0A06`，源频率 10 Hz），RMUL 没有雷达，也没有对哨兵的敌情下发。敌方的位置、血量、弹量、增益、姿态都只能由车载感知获得，或从双方总伤害差与血量变化间接推断局势。

## 6. 选手端与自定义控制器

- `0x0303`（15 字节，P26 表 1-35）：选手端点击小地图后由服务器下发给"发送方选择的己方机器人"，内容含目标地图坐标或目标机器人 ID、键值、来源 ID。**能否选中哨兵、以及 RMUL 下是否允许对哨兵下发，需答疑确认**；U26 对哨兵只写了"1 个调试遥控器"。
- U26 只给英雄、步兵、工程写明"最多配置 1 个遥控器和 1 个自定义控制器"；哨兵这一栏只有调试遥控器。**RMUL 2026 规则手册没有 RMUC 那样的"自定义客户端"章节**。
- P26 §2 是自定义客户端协议，指令包括 `GameStatus`、`Event`、`RobotPosition`、`MapClickInfo`、`MapClickCmd`、`CustomControl`，以及哨兵相关的 `SentryStatusSync`、`SentryCtrlCommand`、`SentryCtrlResult`。协议存在不等于 RMUL 允许使用，V2.0.0 的修改日志还记录了对 `SentryStatusSync`、`SentryCtrlCommand` 的修订。**本条属于最需要答疑的项目。**

## 7. 只能靠本机感知或推断的信息

| 信息 | 合理来源与边界 |
| --- | --- |
| 本机高频位姿、速度、角速度、定位质量 | 本机激光惯性里程计与轮式里程计；1 Hz 的 `0x0203` 只作粗校验 |
| 敌方位置、速度、朝向、瞄准方向 | 车载感知与跟踪；官方无下发 |
| 敌方血量、弹量、热量 | 无官方来源；只能由受击反馈（`0x0206`，无攻击者身份）与观察推断 |
| 队友任务与意图 | 位置序列推断；受 1 Hz 采样限制 |
| 障碍物与视线遮挡 | 本机传感器与地图；通行几何与火力几何分别处理 |
| 区域控制强度、支援价值 | 由已知状态与几何关系构建的模型；官方占领标志不等于实际控制 |
| 复活后的可用时间窗 | 复活血量 20%、无敌 30 秒、虚弱至回补给区解除，全部由本机状态与 `0x020D`/`0x0003` 交叉确认 |

对"零值"要做区分：RMUL 下大量零值是**结构性空槽位**（无该实体），不是"该实体当前为零"。接收侧应按 §4 的表把这些字段显式丢弃，否则会把"没有前哨站"误判成"前哨站已被摧毁"。

| 项 | 现状 | 缺口 |

## 9. 待答疑确认清单

1. `0x020D` 中姿态、立即复活、远程兑换、能量机关标记位在 RMUL 2026 是否有效；若无效，是否有定义"保留位恒零"。
2. `0x020B` 中工程机器人与 4 号步兵槽位在 RMUL 3V3 是否恒零；己方步兵是否固定占 3 号槽位。
3. `0x0003` 中前哨站与基地血量在 RMUL 是否恒零。
4. `0x0101` 在 RMUL 下哪些 bit 有效（补给区、高地、控制区的位定义）。
5. 选手端 `0x0303` 是否允许向哨兵下发。
6. RMUL 2026 是否允许使用自定义客户端（P26 §2），若不允，`SentryCtrlCommand` 是否仅供其他赛事使用。
7. `0x0120` 的"确认复活"在 RMUL 的自动读条复活机制下的含义。
8. P26 自身存在总表长度与详细结构长度不一致的疑点（例如 `0x0203` 总表 16 字节而结构列 12 字节），实现前需一并答疑。

## 10. 结论与接入顺序

1. **信息面比 RMUC 窄得多。** 没有雷达、没有飞镖、没有前哨站基地、不允许多机通信，哨兵的官方输入收敛为"本机状态 + 双方血量与建筑 + 场地事件 + 己方英雄与步兵坐标"。
2. **敌情必须自给。** 世界模型里的敌方部分完全依赖车载感知与推断，感知能力的下限就是战术能力的下限。
3. **全自动与无人干预是前置条件。** 每次上电与每次复活后的定位初始化都要自动完成，这条与 §2 的 R22/R23 直接相关，也决定了重定位模块的优先级高于任何信息接入工作。
4. **建议接入顺序**：`0x0001` / `0x0201` / `0x0202` / `0x0208` / `0x0209`（本机与比赛状态）→ `0x0003` / `0x0101` / `0x0104`（局势与判罚）→ `0x020B`（队友坐标，RMUL 唯一的队友来源）→ `0x020D` 中经答疑确认有效的位（脱战、可兑换数）→ `0x0206` / `0x0207`（受击与射击反馈）。每步都明确来源、时效、以及无数据时的降级行为。
5. **按赛季隔离。** F27 已公布重装机器人取代工程机器人、新增空中机器人与机库、场地新增制高点和隧道、自定义控制器与自定义客户端合并为"自定义终端"且终端可发送"干预哨兵行动"指令。这些会改变 §3 到 §6 的结论，正式规则发布前按待确认处理。注意 F27 的阵容表标注为"RMUC 2027 全程"，同时又给出 RMUL 的放宽说明，涉及 RMUL 的具体条款需答疑确认。
